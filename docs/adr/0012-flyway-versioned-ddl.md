# ADR-0012: DDL 全部 Flyway 版本化

- 状态：已接受
- 日期：2026-10-10
- 影响范围：数据库、交付升级流程

## 背景

私有化交付有一个必然场景：**客户现场从 v1.0 升级到 v1.3**。
升级过程中能不能动数据库、怎么动、动了怎么回退，是交付手册里最关键的一章。

如果依赖：
- `spring.jpa.hibernate.ddl-auto=update` —— 不可预测，可能加错列、删错索引，生产禁用
- 手工执行的 SQL 脚本 + 一张"升级步骤"表格 —— 必然会有人漏执行、顺序错、忘记备份
- 运维手工 psql —— 完全不可追溯

这三种方式在第一个客户的第一次升级时就会出事故。

## 决定

1. **所有 DDL 变更必须通过 Flyway 迁移脚本**（`sql/V<n>__<desc>.sql`），从 `V1__baseline.sql` 开始
2. 已发布的迁移脚本**永不许修改**。要改就追加新脚本
3. 应用启动时自动执行 `flyway migrate`（可配置关闭）
4. 每个迁移脚本头部注释必须包含：变更内容、预期耗时、**回滚说明**
5. 现场升级 SOP：停止应用 → `pg_dump` 备份 → `flyway migrate` → 启动新版本 → 验证

```
sql/
├── V1__baseline.sql              # 初始 schema
├── V2__add_doc_acl.sql
├── V3__add_chunk_page_columns.sql
└── ...
```

## 后果

### 正面
- 数据库状态与代码版本严格对应，任何环境都能重建
- 升级 SOP 可写成三行命令，交付手册极简
- 回滚路径明确（因为有备份 + 明确的迁移点）
- 新环境初始化只需一条 `flyway migrate`
- 数据库演进历史可读——将来想通读 schema 演变，`sql/` 目录就是编年史

### 负面 / 代价
- 加一列这种"小事"也要写一个迁移文件，有仪式感开销
- `chunk` 表在数百万行时加列的锁表风险需要 `ALTER TABLE ... ADD COLUMN ... DEFAULT` 的注意
  （PG 11+ 大部分场景已优化，但加索引仍是重操作，需单独脚本 + 说明）
- 破坏性变更（删列、改类型）必须拆成多个版本：先双写、再迁移、最后清理——
  不能一个脚本搞定，过程更长

## 考虑过的替代方案

| 方案 | 为什么否 |
|---|---|
| JPA `ddl-auto=update` | 不可预测，绝不用于生产 |
| Liquibase | 能力相当，但 XML/YAML 变更集不如纯 SQL 直观，且团队更熟 Flyway |
| 纯手工 SQL + 文档 | 漏执行、顺序错、无回滚，交付现场必出事故 |
| 用 jOOQ / 代码生成管理 schema | 引入额外工具链，2-3 人团队不必要 |

## 验证方式

- `mvn verify` 中包含 `flyway validate`，确保脚本未被事后修改
- 从零环境（空库）执行 `flyway migrate` 后，与生产库 schema diff 为空
- 交付手册中的升级 SOP 在测试环境完整演练过一次（v1.0 → v1.3）
