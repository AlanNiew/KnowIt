# ADR-0014: 引用必须携带页码

- 状态：已接受
- 日期：2026-10-10
- 影响范围：`domain.Citation`、`AnswerComposer`、解析器

## 背景

企业用户对 RAG 的信任建立在一个极简的动作上：**点开引用，看到原文就在那一页**。
做不到这一点，一切"有据可查"都是空话。

市面上大量 RAG demo 的引用只给一个文档名 + 一个相似度分数。
用户点了之后看到整篇文档，自己滚动去找——这个动作的成本足以让用户回到
"我直接全文搜索好了"。

这个问题在 P0 不解决，后面代价极大：
- 页码信息必须在**解析阶段**从 PDF / Word 里提取出来并挂到 chunk 上，
  解析器一旦把页码丢了，要重新跑整个知识库的 ingestion 才能补
- `Citation` 实体如果一开始没有 `page_no` / `char_start` 字段，
  后面加字段要改 DB schema、改 API 契约、改前端——而现场客户的数据已经在库里了

延迟满足在这里**不可用**：这是 P0 必须焊死的纪律。

## 决定

**`Citation` 必须携带页码与原文定位信息，缺一项则该回答视为不可信。**

```java
public record Citation(
    Long chunkId,
    Long documentId,
    String fileName,
    Integer pageNo,        // 必填。非分页格式（txt/md）为 null 但必须有定位
    Integer pageStart,     // parent chunk 的页范围
    Integer charStart,     // 原文偏移，前端精确高亮用
    BigDecimal score,      // rerank 校准分，不是 embedding 相似度
    String snippet         // 引用原文片段
) {}
```

配套规则：
1. **解析阶段必须提取页码**：PDFBox / Tika 解析时记录每段的页码范围，
   Wed 格式同样要从段落位置推断页
2. **页码与切片绑定**：`chunk.page_start` / `chunk.page_end` 在 ingestion 时写入，随 parent-child 结构继承
3. **引用交叉校验**：AI 总结模式下，模型输出的 citations 必须与 `EvidenceBundle` 中的 chunkId 比对，
   模型编造的引用（chunkId 不存在）**直接丢弃并告警日志**
4. 前端点击引用 → 打开文档并**滚动定位到该页 + 高亮该片段**

**宁可少一条引用，不可多一条假引用。**

## 后果

### 正面
- 用户可验证性，是 RAG 在企业场景从"玩具"变"工具"的分界
- 审计与合规友好：制度类问题能精确到"第 X 页第 Y 条"
- 防止模型编造引用——这是本地小模型最常见的失败模式之一
- 调试友好：出问题能精确定位到原文位置，不需要人肉翻文档
- 文档解析质量有了一个可量化指标（引用页码正确率），纳入 knowit-eval

### 负面 / 代价
- **解析器实现更重**：要追踪页边界，对扫描件、无页码文档、HTML 都要有降级策略
  （HTML 无页码 → 用锚点/区块号；扫描件 → P4 OCR 后才有页码）
- 部分格式确实无法给出页码，`pageNo` 允许为 null 的例外要有明确规则
- 交叉校验增加一次 LLM 输出与 bundle 的比对开销（可忽略，纯内存操作）
- `snippet` 冗余存储，chunk 表体积上升

## 考虑过的替代方案

| 方案 | 为什么否 |
|---|---|
| 只给文件名 + 分数 | 用户无法验证，信任建立不起来 |
| 给 chunk 全文 | 泄露上下文结构，且用户还是要自己找 |
| 只给字符偏移不给页码 | 机器友好但对人类不友好，用户看的是页 |
| 用模型自己输出的页码 | 小模型编页码是常态，不可信 |
| P1 再加，P0 先跑通 | 一旦解析器丢页码，要全库重新 ingestion；schema 事后加字段要改现场数据，代价极高 |

## 验证方式

- P0 验收标准第 3 条：10 个文档内问题，回答正确**且引用页码人工核对正确**
- P2 验收：引用页码正确率 ≥ 0.9（纳入 knowit-eval 指标）
- 安全测试：构造一个会诱发模型编造 chunkId 的问题，断言该引用被丢弃且有告警日志
