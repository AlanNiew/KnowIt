# ADR-0006: 摘录模式优先

- 状态：已接受
- 日期：2026-10-10
- 影响范围：generation、产品形态、`AnswerComposer`

## 背景

用户选定了硬件下限为 **8C16G 无显卡**。这个前提推导出一个残酷的结论：

CPU 上跑本地 LLM，瓶颈是 prefill（提示词预填充）。经验值：
4B 量化模型约 10–20 tok/s，1.7B 约 30–50 tok/s。
一次有效 RAG 问答需要 1500–3000 token 上下文，于是首字延迟 40–100 秒。

**这不是"慢一点"，是交互体验崩掉。** 用户点完提问去泡杯茶回来，答案刚开始吐字。

三个选项摆在面前：
1. 把本地 LLM 默认关掉，只做检索 → 产品失去"AI"属性
2. 强行默认 AI 总结 → 客户以为产品坏了
3. 换一个产品形态

## 决定

**默认问答模式是摘录模式（`EXCERPT`），不调用 LLM。**

```
提问 → 混合检索 topN → rerank 校准 → 直接呈现原文片段（关键词高亮 + 页码）
                                        ↘ [让 AI 总结] 按钮（用户主动触发，愿意等）
```

有 GPU（标准档及以上）时，`AnswerComposer` 自动切换为 AI 总结模式。
用户也可以在界面上手动切换。

两种模式的取舍：

| | 摘录模式 | AI 总结模式 |
|---|---|---|
| LLM 调用 | 无 | 有 |
| 延迟 | <1s | POC 档 40–80s / 标准档 3–8s |
| 幻觉风险 | **零**（原文就是答案） | 有，靠证据分级 + 引用校验压制 |
| 可解释性 | 100%，用户自己看原文 | 依赖模型转述 |
| 适用查询 | 制度条款、规范条文、参数表 | 跨段落综合、对比、归纳 |

## 后果

### 正面
- **弱硬件下依然有可用的产品**：客户机器再差，系统依然秒回
- 零幻觉、100% 可解释——对"制度依据"这类场景，用户要的就是原文，**不需要 AI 改写**
  问"报销上限是多少"，答案是"《差旅费管理办法》第 12 条：单次不超过 2000 元"，
  这比一段 AI 总结更可信也更有用
- LLM 从"必需品"变成"增强项"，硬件门槛从"必须有显卡"降到"有最好，没有也行"
- 系统在没有 LLM 容器的情况下依然能完整工作（LLM 挂了不影响查询）
- 省 token、省电、省算力成本

### 负面 / 代价
- **产品的"AI 感"被削弱**。第一次演示时，用户看到的是高亮原文而不是 AI 生成的回答，
  心理预期会落差。必须靠产品文案提前说明（"基于您文档的可信回答"）
- 对"帮我归纳这五份文档的共性"这类**跨文档综合问题**，摘录模式无能为例，
  只能引到很多原文让用户自己读。这类问题在 CPU 档只能引导用户点"AI 总结"并接受等待
- 前端交互复杂度上升（两种模式、一个"愿意等"的按钮）
- 评测指标要分开统计（摘录模式的"正确率"= 检索正确率，不含生成）

## 考虑过的替代方案

| 方案 | 为什么否 |
|---|---|
| 强行默认 AI 总结 | POC 档首字 40–100s，客户会认为产品不可用 |
| 降低上下文预算到 512 token 硬上 | 上下文不够，检索 5 个 chunk 只能塞 2 个，召回质量崩 |
| 用云端 LLM 兜底 CPU 场景 | 数据出境，违背立项目标（ADR-0002） |
| 强制要求客户上 GPU | 把大量中小企业挡在门外，失去市场 |
| 用更小的模型（0.6B） | prefill 能到 80 tok/s，但 0.6B 中文能力和指令遵循太差，引用格式都hold不住 |

## 验证方式

- P0 验收标准第 6 条：8C16G 实测 AI 总结模式首字延迟，确认摘录模式作为默认的合理性
- 黄金 50 问中，摘录模式的检索正确率 ≥ AI 总结模式的 90%
   （若差距过大，说明检索侧还有提升空间，与生成无关）
- 无 LLM 容器的降级演练：`docker compose stop llm` 后，系统全部查询功能正常
