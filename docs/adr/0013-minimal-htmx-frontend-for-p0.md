# ADR-0013: P0 用零构建 htmx 前端

- 状态：已接受
- 日期：2026-10-10
- 影响范围：P0 交付方式、`knowit-server` 静态资源

## 背景

2-3 人团队，成员是 Java 背景。前端如果一上来就搞 Vue 3 + TypeScript + Vite + Pinia + Element Plus：
- 需要专职前端，或者某个后端同学分心去学
- 多一个工程、多一条构建链、多一个 CI 任务
- 前后端联调增加一个 CORS / 代理 / 构建产物拷贝的麻烦
- **最关键的是**：P0 的目标是验证"全本地 + 单 PG + 弱硬件"的 RAG 闭环能否跑通。
  前端精美与否对这个目标毫无贡献，但它会实实在在地拖慢验证。

P0 需要的东西其实很少：一个输入框、一个提交按钮、一段 Markdown 渲染、一个 SSE 连接、
一个文件上传、一个知识库下拉、一个引用脚注列表。这些用不到框架。

## 决定

**P0 前端是一个零构建的单页 HTML**，放在 `knowit-server/src/main/resources/static/index.html`，
由 Spring Boot 直接托管。

技术选择：
- **htmx**：声明式属性驱动请求，`hx-post` / `hx-target`，几千字节
- **htmx SSE 扩展**：处理流式对话
- **Alpine.js**：少量客户端状态（当前知识库、当前模式、上传进度）
- **marked**：Markdown 渲染
- **highlight.js**：代码高亮
- **DOMPurify**：XSS 防护（RAG 输出原文，必须转义）

全部通过 CDN 引入（开发期）或下载到 `static/vendor/`（私有化离线部署）。
**没有 npm、没有 node_modules、没有构建步骤。**

```
mvn spring-boot:run   →   http://localhost:8080 就是完整可用的界面
```

## 后果

### 正面
- **P0 完全不被前端阻塞**：后端同学一两天就能出界面
- 零构建链，私有化部署少一层依赖，离线环境友好
- 调试极简单：浏览器 DevTools 直接看 HTML，没有 source map / HMR / 打包混淆
- 后端交付物就是一个 fat jar，前端嵌在里面，运维只跑一个进程

### 负面 / 代价
- **这是要还的债**：交互复杂度一上来（多轮会话管理、侧边栏、设置面板、权限管理、文档预览），
  htmx 会开始捉襟见肘。P3 之前必须重写成 Vue 3
- 复用性差：htmx 的模板片段逻辑散落在 HTML 属性里，复杂状态难维护
- 团队若没人写过 htmx，有几十行的学习成本（很小）
- 无法做代码分割、Tree shaking、组件库复用

## 考虑过的替代方案

| 方案 | 为什么否 |
|---|---|
| P0 就用 Vue 3 + Vite | 阻塞 P0 进度，且对验证 RAG 闭环毫无贡献 |
| Thymeleaf 服务端渲染 | SSE 流式对话体验差（要 chunked encoding + flush），且每次交互刷新整页 |
| 先只提供 REST API，用 curl 验证 | 验收标准 1-4 条要求"能用"，没有界面演示和评测都会很别扭 |
| Vaadin Flow（纯 Java 前端） | 对 Java 团队友好，但服务端状态 + 长连接模型与 SSE 流式聊天有摩擦，学习成本也不低 |

**重写时机**：P3 开始产品化（管理后台、权限设置、文档预览）时重写为 Vue 3。
接口层（REST + SSE）从 P0 就按标准设计，重写前端不影响后端一行代码。

## 验证方式

- P0 验收标准第 1 条：`docker compose up` 后 `:8080` 见到可交互界面，无任何 npm 步骤
- `static/index.html` 体积 < 500 行，不含业务逻辑，只做请求与渲染
- 界面源码中无业务规则（切片参数、权限判断都不在前端）
