# ADR-0001: 用 ADR 记录架构决策

- 状态：已接受
- 日期：2026-10-10
- 影响范围：全项目

## 背景

KnowIt 是一个要长期维护的开源项目，且定位为"技术作品"。
架构决策一旦散落在 commit message、IM 聊天和某次代码评审里，
三个月后没人记得为什么 `chunk` 表要冗余 `kb_id`，
新人只能靠考古，最后得出结论"这是历史包袱"然后删掉。

尤其本项目有大量反直觉的决策（摘录模式优先、不在 PG 装中文分词扩展、
AccessContext 为什么必须是入参而不是 ThreadLocal）——
这些决策**看起来很怪**，没有记录的话第一个 PR 就会来"优化"它们。

## 决定

所有不可逆或难以逆转的架构决策，必须写成一条 ADR，存放在 `docs/adr/`，
编号递增，永不删除。被取代的 ADR 状态改为"已取代"并指向新的。

决策是否"值得写 ADR"的判据：
- 换掉它需要改多个模块或数据模型 → 写
- 它看起来不符合直觉，需要解释 → 写
- 它引入了长期维护成本（新依赖、新运维组件）→ 写
- 换个变量名、换个方法内部实现 → 不写

## 后果

### 正面
- 新人 onboarding 从"问人"变成"读文档"
- Code review 可以引用 ADR 编号作为依据，减少无休止争论
- 事后复盘有据可查，不会再犯第二次同样的错

### 负面 / 代价
- 写 ADR 有真实开销，一个决策要花 20–40 分钟
- 容易写成流水账或事后合理化。缓解：负面后果必须写，写不出来说明没想清楚，不许标"已接受"

## 考虑过的替代方案

| 方案 | 为什么否 |
|---|---|
| 只写注释和 Javadoc | 粒度太细，看不到全局；注释会随代码漂移失效 |
| 只写一份大设计文档 | 无法表达"决策随时间的演变"，新人分不清哪些还作数 |
| 写在 Wiki / Notion | 与代码分离，必然腐烂；必须跟仓库一起版本化 |
| 不记录，靠口口相传 | 2-3 人团队短期可行，开源后不可行 |

## 验证方式

- 新人第一个 PR 能在不问任何人的情况下，说出 `retrieval` 为何不能依赖 `generation`
- 每一条 PR 中"为什么不直接用 X"的质疑，都能在 ADR 索引里找到对应条目
